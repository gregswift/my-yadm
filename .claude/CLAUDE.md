# Worktree discipline (all repos using the bare + worktrees layout)

- Every branch gets a persistent worktree, created with `git new-worktree <branch>` (the repo's sibling-worktree layout). Never `checkout -b` inside an existing worktree, and never build branches in throwaway `git worktree add` dirs that get deleted after pushing.
- This applies to subagents too: when delegating implementation that creates or rewrites branches, instruct the agent to create/use the persistent per-branch worktrees, not temp ones. A branch that exists only as a local ref (no worktree) is invisible to `git refresh --stack`/`--all` and will be stranded by the next refresh.
- After any out-of-band force-push to a branch (e.g. by an agent in another session), reset the branch's worktree to origin before running `git refresh` there, so a stale local can't be replayed over origin's newer content.
- For stacked branches, prefer `git refresh --stack` for main-catchup; verify with `-n` first, and always build/test at the affected stack points before pushing rebases.

# Working with Makefiles

The Makefile is the interface to a repo. Every repo exposes the same verbs, so a command learned in one repo works in all of them.

## Structure

- Order the head of the file: `.POSIX:`, `#Serial YYYYMMDDNN`, includes, `?=` defaults, computed `:=` values, `export`, then targets.
- Load overrides in this order, each with a leading dash so a missing file is silent: committed repo config (`.config.include.mk`), personal and gitignored (`local.include.mk`), then `$(CI_MAKE_OVERRIDES)`.
- Use `?=` for anything a developer or CI may override. Use `:=` for git ref, buildstamp and version, so a computed tag cannot drift mid run.
- Registry identity lives in the committed config include, never inline. When there is no safe default, fail on `$(origin VAR)` undefined with `$(error)`.
- A Makefile carrying the managed-file banner is changed in the related template and the Serial is bumped, never edited in place.

## Container first

- No toolchain on the host. A container engine is the only local requirement. npm, uv, cargo, pytest, ruff, tsc and opa each run through a `$(CONTAINER_ENGINE) run` wrapper. If no direct image is available, prompt user with options.
- Wrappers layer: `BASE_COMMAND`, then a language command, then a tool command. A new target reuses them instead of writing a fresh `run` invocation.
- Pin every tool image as an `X_CONTAINER_IMAGE` plus `X_CONTAINER_VERSION` pair.
- When mounting a directory to a container, always use `:z` for shared mounts and `:Z` for standalones in both Makefiles and compose files. `:Z` gives one container a private SELinux label, so a second container mounting the same directory locks the first out of its own files. One file using `:Z` is enough to cause it.
- `CONTAINER_SWITCHES ?= --rm -it` locally. CI drops `-it` and switches output configurations through `.github/ci.override.mk`.

## Target vocabulary

- Keep these names and meanings: `help`, `setup`, `lint`, `format`, `typecheck`,
  `test`, `test-unit`, `test-integration`, `check`, `build`, `build-container`,
  `start`, `stop`, `shell`, `repl`, `clean`, `update`, `update-dependencies`,
  `publish`, `publish-container`, `debug-%`.
- `check` is the aggregate gate and CI's only entry point. CI calls `make check`, not the individual tiers.
- `all: help`, and `help` is generated by awk from `## ` comments. Every public target ends with one.
- `run-%` is for a human at a keyboard. It never appears in a workflow or a script. Can appear in a troubleshooting section of developer documentation.
- Mark a target `.PHONY` unless it produces a file of that name. A target sharing a name with a directory, such as `certs` or `docs`, is reported as already done without it.
- Gate expensive idempotent work on a sentinel the tool itself writes, such as `node_modules/.package-lock.json` or `.container`.

## Images and secrets

- Never build, push or reference `latest`. The primary tag is `<version>-<buildstamp>`, with alt tags for version, version plus git ref, and branch.
- Image tags drop the leading `v` via `$(patsubst v%,%,...)`. Git tags keep it.
- Set the OCI created, revision and version labels from the computed build info.
- Generate dev certificates and secrets on demand into gitignored paths. No repo holds a credential, including one that only works locally.

## Compose runtime

- compose is the local runtime. `start` brings the stack up detached, `stop` takes it down, and `test-integration` depends on `start` and leaves it running.
- Set `COMPOSE_PROJECT_NAME` from repo plus sanitized branch. The default is the directory name, which is the branch under the worktree per branch layout, so it collides across repos.
- `PORT_BASE` is the single port knob. Offsets are convention: +0 the service, +1 its database, one slot per further dependency.

## Volumes and state

- Mount a named volume at the path the image declares as its volume. Read it with `image inspect --format '{{.Config.Volumes}}'` rather than from memory, and read it again on every image bump.
- A stale mount path fails silently. The server initializes into an anonymous volume, the named volume stays empty, and the data disappears on recreate.
- CI's `tmpfs` path tracks the same declared volume path as the dev mount.
- A stateful volume belongs to the major version of the server that wrote it. `stop` drops volumes, so crossing a major recovers by recreating the stack.

# Documenting when coding and proposing PRs

Principles:
- Code says what. If the code can show it, nothing else should say it.
- Comments say why — only what the code cannot: an external constraint, a command that doesn't do what it reads like, an approach that fails, a measurement behind an odd bound. Three sentences max; a comment needing a paragraph is mislocated.
- Commits / PR bodies carry the change's rationale — the problem being solved and why this implementation, never a restatement of what the diff shows.
- Documentation (README, decision record, playbook) is where paragraph-length explanation lives: operational context, contracts, how-tos. When a comment wants to grow, it moves here and the comment becomes a one-line pointer.

Supporting rules:
- Wrap commit bodies at 100 characters, matching Conventional Commits `body-max-line-length`. commitlint enforces this in CI.
- PR bodies are not commits and are never wrapped. One line per paragraph.
- Name the specific wrong action a reader takes without this comment. If you can't name it, there's no comment. Then check the other tiers: if the code already shows it or if the commit body or the doc already says it, there's still no comment.
- A comment that contrasts before and after belongs in the commit. If it says "used to", "no longer", "now X instead of Y", or names what the change replaced, it is change rationale, not a why-comment.
- Writing should always be plain style: one idea per sentence, ≤20 words, no figures of speech or idioms.
- Identify the styling pattern inherent to the file you are editing. If no style exists, default to the recommended styling of the language. Change should not look different than the rest of the file. Prompt if inconclusive.
- Answer the question a conditional comment raises.
- File headers say purpose, function headers give the contract.
- Always state full phrasing on first use of an acronym in a file or commit.
- Re-run the tests on every commit in the diff before pushing, reading it as if someone else wrote it, with delete as the default verdict.
